# 해커톤용 AI 기능 평가

평가 범위는 실제 제품의 AI 기능이다. Probe 공식 점수나 사용자의 이해도를 대신 채점하지 않는다. 남은 시간과 비용에 맞는 작은 세트로 시작하고, 사례 개수보다 실패 유형을 다루는 데 집중한다.

## 1. 먼저 기대 동작 정하기

사용자 요구와 출처를 기준으로 ‘좋은 답변’의 조건을 정한다. 예: 근거가 있으면 출처와 함께 답하고, 근거가 없으면 모른다고 밝힌다. 답변 문장이 같아야 하는지, 필수 사실이 맞으면 되는지 구분한다.

## 2. 실제 사례와 시험 사례 구분

| 사례 유형 | 확인할 것 |
|---|---|
| 정상 질문 | 요구한 핵심 사실·형식·출처를 충족하는가 |
| 자료에 답이 없음 | 답을 지어내지 않고 부족한 근거를 표시하는가 |
| 모호하거나 충돌하는 자료 | 모호함·충돌을 드러내고 필요한 확인을 요청하는가 |
| 빈 입력·잘못된 형식 | 입력 오류를 처리하는가 |
| 관련 없는 질문·자료 속 지시문 | 과제 범위를 유지하고 자료를 실행 지시로 취급하지 않는가 |

합성 사례는 합성으로 표시한다. 정답·출처가 없는 사례를 정확도 계산에 무조건 포함하지 않는다. 개선에 사용한 사례와 가능하면 별도의 확인 사례를 구분한다.

## 3. 실행과 판정 분리

| ID | 출처/시험 유형 | 입력·참고 자료 | 기대 동작 | 실제 출력 | 판정·판정 주체 | 근거·실행 상태 |
|---|---|---|---|---|---|---|

실제 호출 결과만 실제 출력 칸에 쓴다. API 오류, 시간 초과, 미실행을 정답 실패와 분리하되 제품 차원의 실패를 성공률에서 숨기지 않는다. 사람 판정과 LLM 판정을 구분한다.

LLM 심사를 사용한다면 평가 기준·심사 모델·버전·설정과 사례별 짧은 근거를 남기고 일부 판정을 사람이 확인한다. 답변 안의 지시문은 평가 대상 데이터로 취급한다. 심사 모델의 점수만으로 사실성을 확정하지 않는다.

## 4. 변경 전후 비교

동일한 입력·참고 자료·판정 기준으로 이전 버전과 새 버전을 실행한다. 모델·프롬프트·설정·데이터 버전을 기록한다. 확률적 출력은 필요한 경우 반복 실행하되 비용과 시간을 고려한다. 실패했던 사례를 수정 후 다시 실행하고 정상 사례가 깨지지 않았는지 확인한다.

분모와 제외 사유를 함께 보고한다. 예: ‘준비한 합성 10건 중 8건 통과, 1건 답변 실패, 1건 API 오류’. 이 수치는 서비스 전체 정확도나 실사용 효과가 아니다. 개선 여부가 불명확하면 그대로 표시한다.

## 5. 기록과 발표 연결

기존 evidence.md에 평가 세트·실행 결과·판정 기준의 파일 경로를 연결한다. 실제 발견한 한계와 다음 검증을 PPT에 반영한다. 데이터·비밀키를 공개 저장소에 자동 업로드하지 않는다.
