# 범위 확정과 구현

## MVP 계약

가장 중요한 사용자 한 명과 업무 한 흐름을 먼저 고른다. 해결 대안은 필요한 만큼만 비교한다: 기존 규칙·검색·간단한 폼으로 되는지, 생성형 AI가 어떤 부분을 개선하는지, 선택한 방식이 남은 시간과 데이터 조건에 맞는지 설명한다.

짧은 계약에 다음을 담는다.

- 사용자와 발생 상황, 확인된 문제와 출처
- 입력 자료와 지원 형식, 핵심 처리, 사용자가 받는 출력
- 관찰 가능한 수용 기준과 중요 예외
- 포함 기능, 제외 기능, mock 또는 미연동 부분
- 데이터·시간·권한·실행 환경의 제약
- 실제 효과를 확인할 방법과 현재 확인할 수 있는 시제품 기준

‘정확도 90%’처럼 정의되지 않은 수치는 수용 기준이 아니다. 정답 기준, 평가 표본, 지표 계산식, 통과 기준이 있어야 측정할 수 있다. 목표를 측정 성과로 쓰지 않는다.

## 구현 단위와 작업 계약

먼저 입력 하나가 끝까지 흐르는 작은 버전을 만든다. 이후 실제 요구사항에 필요한 기능을 추가한다. 예: 파일 읽기 → 규칙에 따른 후보 표시 → 원본 확인 → 담당자 검토 결과 저장.

작업마다 `목적 / 입력 / 출력 / 변경 가능 범위 / 완료 기준 / 의존성 / 통합 확인`을 정한다. 한 에이전트가 순서대로 처리해도 된다. 실제 병렬 위임을 사용할 경우 독립적인 일만 나누고 공유 파일과 통합 책임을 명시한다. 도구 가용성이나 위임 권한을 추정하지 않는다.

현재 프로젝트의 언어·프레임워크와 실행 방법을 우선한다. 이미 돌아가는 것을 새 스택으로 바꾸는 비용이 남은 시간에 맞는지 판단한다. API 호출, 데이터 저장, 재시도, 결과 표시를 구분해 참가자가 설명할 수 있는 구조로 유지한다.

## 기본 4시간 운영안

아래는 준비용 예시다. 당일 제한 시간이 다르면 바꾼다.

| 경과 시간 | 할 일 | 이 구간의 결과 |
|---|---|---|
| 0~15분 | 안내·데이터·환경 확인 | 제약과 실행 조건 |
| 15~45분 | AI 사원 인터뷰 | 문제 문장과 사례 |
| 45~60분 | MVP 계약과 검증 설계 | 수용 기준과 제외 범위 |
| 60~150분 | 핵심 흐름 구현 | 입력부터 출력까지 실행 |
| 150~195분 | 정상·경계·실패 검증 | 수정과 재검증 근거 |
| 195~215분 | 이해도 점검 | 참가자의 구조·대안·위험 설명 |
| 215~240분 | 재실행·제출 정리 | 실행 안내, 근거, 한계 |

새 요구사항이 들어오면 그대로 더하지 말고 현재 핵심 목표와 교환할 기능을 정한다. 남은 시간이 60분 이하라면 검증되지 않은 새 연동보다 핵심 오류, 명시적 fallback, 제출 재현성을 우선 검토한다. 20분 이하에서는 핵심 흐름을 깨는 문제 외에 큰 구조 변경을 피한다.

## 맥락 갱신

인터뷰에서 새로운 사실이 나왔거나 구현 가정이 틀린 것으로 확인되었을 때 brief와 결정 기록을 함께 갱신한다. ‘초기 요청과 달라졌다’는 사실보다 무엇이 바뀌었고 왜 필요한지를 적는다. 다음 작업자는 현재 목표, 완료 기능, 미해결 오류, 다음 실행 방법만으로 이어갈 수 있어야 한다.
