# AI 사원 인터뷰와 문제 정의

사원에게 원하는 기능을 나열하게 하기 전에 실제 업무 사례를 확보한다. 이미 답변된 사항은 생략하고, 다음 설계 결정을 바꿀 질문부터 묻는다. 질문을 한꺼번에 길게 쏟아내지 말고 한 번에 1~3개를 제안한다.

## 질문의 방향

1. 가장 최근 문제 사례: 누가 언제 무엇을 하다가 막혔는가? 입력 자료와 실제 결과를 보여줄 수 있는가?
2. 현재 처리 흐름: 문제를 발견하고 판단하고 조치하는 사람은 각각 누구인가? 어디서 기다리거나 재작업하는가?
3. 영향: 빈도·건수·소요 시간·누락·손실 중 확인 가능한 수치는 무엇인가? 수치의 기간과 분모는 무엇인가?
4. 정상과 예외: 잘 처리된 사례는 어떤가? 사람이 일부러 처리하지 않는 예외도 있는가?
5. 제약: 쓸 수 있는 데이터, 연결 가능한 시스템, 판단 권한, 지켜야 할 금지 행동은 무엇인가?
6. 수용 기준: 이번 시제품에서 반드시 확인해야 할 한 가지 결과는 무엇인가? 어떤 실패가 가장 치명적인가?

기술 선택과 무관한 질문은 뒤로 미룬다. 예를 들어 답변이 DB 필요 여부를 바꾸는지, 실시간 대신 일괄 처리로 가능한지, 자동화 대신 검토 지원이 필요한지를 함께 적는다.

## 문제를 되짚는 문장

“제가 이해한 문제는 [사용자]가 [상황]에서 [현재 방식의 제약] 때문에 [관찰된 업무 영향]을 겪는다는 것입니다. 이번에는 [검증 가능한 결과]까지 해결하고 [범위 밖]은 제외하려고 합니다. 잘못 이해한 부분이나 반드시 포함할 예외가 있나요?”

실제로 확인받기 전에는 ‘확인 요청안’으로 표시한다. 답변이 없으면 확인됐다고 쓰지 않는다. 코딩은 업무 결과를 바꿀 핵심 불확실성을 먼저 줄인 뒤 진행하되, 이미 구체적인 과제가 제공됐으면 인터뷰를 반복하지 않는다.

## 예시 — 과거 프로게이머 인터뷰 문제

사용자가 제공한 사실은 ‘선수와 매니저의 시간이 불규칙해 인터뷰 연습 일정을 맞추기 어렵다’는 것이다. 여기서 ‘질문 생성 AI가 필요하다’, ‘실시간 음성 인식이 필수다’, ‘매니저 업무가 80% 줄어든다’는 결론은 아직 나오지 않는다.

우선 연습이 누락되는 주된 이유, 선수 혼자 연습할 수 없는 이유, 매니저가 보는 기준, 답변에서 피해야 할 내용, 경기별 질문 자료가 있는지 확인한다. 이에 따라 비동기 연습, 근거 있는 피드백, 매니저 검토용 요약을 작은 흐름으로 만들 수 있다. 음성 기능은 실제 수용 기준에 필요할 때 선택한다.

## 반도체 과제에 적용할 때

교대 인수인계, 경보 검토, 품질 데이터 정리, 절차 문서 검색 등은 연습 주제이지 실제 SK하이닉스 출제 내용이 아니다. 다른 회사의 공장 기준·MES 스키마·결함 정의를 해당 기업의 사실로 가져오지 않는다.

기록 공란이 ‘문제 없음’인지 ‘측정 안 됨’인지부터 확인한다. 시간대·단위·설비 ID·lot·중복·교대 경계의 의미를 데이터 소유자에게 묻는다. 제어 권한이 없는 과제는 검토 지원으로 범위를 잡는다.
