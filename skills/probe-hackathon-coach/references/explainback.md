# 참가자 이해도 점검

평가의 대상은 AI가 쓴 설명문만이 아니라 참가자의 실제 이해다. 코드·동작·테스트 등 제공된 실제 산출물에 연결해서 질문한다. 코드가 없으면 그 한계를 먼저 밝히고 개념 연습으로 진행한다.

## 진행 방법

한 번에 질문 하나를 내고 참가자의 답을 기다린다. 먼저 모범답안을 전부 보여주지 않는다. 답을 받으면 맞은 점, 빠진 점, 실제 근거를 짧게 알려주고, 필요한 경우 다른 사례로 다시 확인한다. 사용자가 일괄 질문 목록을 요청하면 목록을 주되 이해가 확인된 것으로 처리하지 않는다.

Probe 실전 모드에서는 마지막 발표 연습에만 몰아서 하지 않는다. 첫 핵심 흐름 완성이나 중요한 방향 전환처럼 설명이 도움이 되는 시점에 한 질문을 끼워 넣는다. 모든 변경에서 반복하지 않으며, 사용자가 작업을 계속하라고 하면 이해 상태를 미확인으로 두고 허용된 작업을 진행한다.

질문은 필요한 범위에서 세 영역을 오간다.

| 영역 | 질문 예 | 확인할 내용 |
|---|---|---|
| 동작·위험 | 이 입력의 날짜가 해석되지 않으면 사용자에게 무엇이 보이나요? | 실행 전 예측, 예외 경로, 영향 |
| 구조 | 입력 파일의 한 행이 최종 결과에 나타날 때까지 어디를 지나나요? | 데이터 흐름, 각 구성요소 책임 |
| 결정·근거 | 이 부분에 LLM을 쓴 이유와 규칙으로 처리한 부분은 무엇인가요? | 대안, 선택 조건, 비용·정확성의 tradeoff |

추가 질문: 어떤 결과를 믿으면 안 되는가? 테스트가 통과해도 남는 위험은 무엇인가? 데이터가 10배가 되면 무엇부터 확인할 것인가? AI의 초기 제안 중 무엇을 수정했고 어떤 근거가 있었는가?

AI 내부의 숨은 사고 과정을 요구하지 않는다. 검토 가능한 설계 이유, 대안 비교, 코드·문서·테스트 근거를 설명한다.

## 이해 확인 상태

`직접 설명 확인 / 일부 설명·보완 필요 / 아직 답변 안 함`으로 기록한다. AI가 대신 작성했거나 참가자가 읽기만 한 내용은 직접 설명 확인에 해당하지 않는다. 발표 대본은 이 점검 이후에 만들면 참가자가 설명할 수 있는 범위와 자연스럽게 일치한다.

## 3분 설명 구성

누구의 어떤 문제가 있었는지 → 어떤 근거로 범위를 골랐는지 → 입력부터 출력까지 시연 → 왜 이 구조를 선택했는지 → 무엇을 실제로 검증했고 무엇이 남았는지.

과장된 성과보다 확인한 기능·한계·다음 검증을 정확히 말한다.
