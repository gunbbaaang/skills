# Probe 실전 사용 순서 — 웹과 PPT까지

이 문서는 참가자가 복사해 사용할 수 있는 진행 예시다. 공식 대회 시간·제출 형식·도구 규칙을 우선한다. 아래 시간표는 **4시간이라고 가정한 준비안**이며 실제 규정이 아니다.

평가항목에 맞춰 무엇을 판단하고 검증할지 보면서 진행하려면 **[고득점 준비 실전 가이드](score-playbook.md)**를 사용한다. 16개 항목 연결표, 인터뷰부터 제출까지의 시나리오, 복사용 요청문을 담았다. Codex에는 `고득점 준비 가이드를 적용하고 현재 진행표를 보여줘`라고 요청한다. 두 문서의 시간표는 각각 제작 도구 선택과 평가 준비에 초점을 둔 대안이며 합산하지 않는다.

## 시작할 때 한 번

설치를 마친 뒤, 평가받는 환경 안의 Codex 대화창에 넣는다.

```text
$probe-hackathon-coach
Probe 실전 모드로 진행해줘. 이 터미널에서 너와 나누는 대화가 평가 대상이야.
과제와 대회 안내, AI 사원 대화 내용을 차례로 붙여줄게.
현재 문제·근거·성공 기준·선택 이유·실제 검증 결과·다음 행동을 기록하며 진행하자.
확인 사실, 내 판단, 네 제안, 미검증 가설을 구분해줘.
기존 기록 파일을 재사용하고 중요한 변경과 검증은 대화에도 짧게 설명해줘.
내가 웹이나 PPT를 요청하면 설치된 제작 스킬 중 필요한 것만 사용해줘.
남은 시간: [실제 남은 시간]
과제·공식 안내: [여기에 붙여 넣기]
```

스킬은 같은 과제 안에서 계속 적용한다. 매 메시지마다 긴 시작 문장을 반복하지 않아도 된다. 새 세션에서는 인계 문서를 읽고 다시 실전 모드를 지정한다. 설치는 작동 방식 안내를 추가하는 것이며, 자동 녹화나 Probe의 수집 범위를 바꾸지 않는다.

## 1. AI 사원에게서 사실 확보

AI 사원과의 대화를 Codex에 붙이고 다음처럼 요청한다.

```text
이 대화에서 확인된 사실과 미확인 가정을 나누고, 실제 최근 업무 사례·현재 처리 방식·실패 시 영향·시간과 데이터 제약을 더 확인할 질문을 골라줘.
내가 바로 사원에게 물어볼 수 있도록 짧게 써줘.
```

매 답변을 받은 뒤 중요한 새 근거만 추가한다. 해결책을 먼저 확정하기보다 반복되는 불편과 실제 업무 조건을 확인한다. Codex가 제안한 추측을 사원 답변으로 기록하지 않는다.

## 2. 해결할 문제와 완료 기준 확정

```text
확인한 근거로 이번에 해결할 문제를 한 문장으로 정리해줘.
사용자 한 명의 핵심 흐름, 입력과 출력, 검증 가능한 완료 기준, 이번에 제외할 범위를 정하자.
가능한 접근을 비교하되 남은 시간과 제공된 데이터에 맞게 추천해줘.
```

참가자가 선택 이유를 자기 말로 덧붙인다. 예: “실시간 참석이 어렵다는 조건이 확인돼 비동기 방식으로 진행하겠습니다.” AI가 만든 설명을 참가자의 판단으로 간주하지 않는다.

## 3. 웹이 필요할 때

새 웹 화면을 만들 때:

```text
$frontend-design
합의한 문제와 완료 기준으로 핵심 사용자 흐름이 작동하는 웹 MVP를 만들어줘.
대상 사용자: [사용자]. 반드시 되는 흐름: [입력 → 처리 → 결과].
기존 기술 구성이 있으면 그대로 사용하고, 한국어·모바일 화면·키보드 사용을 고려해줘.
로딩·빈 결과·오류 상태도 구현하고 실제 연동과 샘플 데이터를 구분해줘.
실행 방법과 내가 직접 확인할 동작을 알려줘.
```

React/Next.js라면 `vercel-react-best-practices`를 필요한 부분에 적용한다. 이 스킬 때문에 HTML 프로젝트를 React로 바꾸거나 기능과 무관한 최적화를 시작하지 않는다.

작동하는 흐름이 나온 뒤:

```text
$webapp-testing
합의한 완료 기준을 바탕으로 핵심 흐름을 실제 브라우저에서 검증해줘.
정상 입력과 중요한 잘못된 입력, 실패 후 복구를 확인하고 예상·실제 결과를 기록해줘.
실패하면 수정한 뒤 같은 조건으로 다시 확인해줘. 미실행은 미실행으로 남겨줘.
```

화면 사용성을 빠르게 점검할 때:

```text
$web-design-guidelines
현재 MVP의 입력 화면과 결과 화면을 검토해줘.
키보드 포커스, 입력 라벨, 오류 안내, 모바일 잘림 중 사용자 작업을 막는 문제부터 찾아줘.
시간 안에 고칠 우선순위를 제시해줘.
```

현황판은 `visual-explainer`, 사용자가 실제로 업무를 처리할 웹 MVP는 `frontend-design`으로 구분하면 요청이 명확해진다. 웹 공개 배포 여부는 당일 요구와 사용자 요청에 따른다.

## 4. PPT가 필요할 때

핵심 흐름과 검증 자료가 준비되면 만든다. 실측 근거가 없을 때 발표용 수치를 채워 넣지 않는다.

```text
$slides
현재 프로젝트 기록과 실제 구현·검증 결과로 [발표 시간]분 발표용 한국어 PPT를 만들어줘.
문제와 사용자 → 인터뷰 근거와 제약 → 선택한 해결책 → 작동 흐름 → 검증 결과 → 한계와 다음 단계로 구성해줘.
편집 가능한 .pptx와 재생성용 소스를 함께 만들어줘.
실측 결과, 합성 데이터, 목표치를 구분하고 가능한 렌더링·잘림 검사를 수행해줘.
확인하지 못한 항목은 따로 알려줘. 공식 템플릿이 있으면 그것을 우선해줘.
```

6장은 짧은 발표의 시작 예시일 뿐이다. 제출 형식과 발표 시간을 확인해 장수를 조절한다. 원래 PPT 제출이 필요하지 않으면 구현·검증 시간을 우선한다.

## 5. 기록 확인, 인계, 제출

데이터를 받았거나 AI 응답 품질·발표 수치를 검증해야 하면 [데이터·AI 검증 스킬 사용 가이드](evidence-skills.md)를 참고한다. 데이터는 `explore-data`로 파악하고, 수치는 `validate-data`, 차트는 `data-visualization`, AI 응답은 `llm-evaluation`, 재현되는 오류는 `systematic-debugging`으로 필요한 부분만 보강한다.

- 현황 확인: `$visual-explainer 기존 기록으로 현재 목표·결정 이유·검증 상태·다음 행동을 한 화면에 보여줘. 원본 경로와 갱신 시각을 넣어줘.`
- 세션 인계: `$handoff 다음 세션이 이어갈 수 있게 probe-notes/HANDOFF.md에 목표·현재 상태·미해결 문제·다음 행동을 적고 기존 근거 파일은 경로로 연결해줘.`
- 새 세션: `probe-notes/HANDOFF.md와 연결된 기록을 읽고 Probe 실전 모드로 이어가줘. 먼저 현재 코드와 기록이 일치하는지 확인해줘.`
- 제출 직전: `$probe-hackathon-coach 핵심 흐름을 다시 검증하고 실행 방법·실제 연동과 mock·남은 한계를 점검해줘. 내가 구조와 선택 이유를 설명할 수 있는지도 중요한 질문부터 확인해줘.`

## 4시간 준비용 배분 예시

| 경과 시간 | 집중할 것 | 남길 근거 |
|---|---|---|
| 0–35분 | 업무 인터뷰와 문제 확인 | 실제 사례, 제약, 미확인 조건 |
| 35–50분 | 범위와 완료 기준 | 선택 이유, 핵심 흐름, 제외 범위 |
| 50–155분 | 작은 작동 단위로 구현 | 구현 위치, 중간 검증과 변경 이유 |
| 155–195분 | 핵심 흐름·오류·화면 검증 | 예상/실제 결과, 수정 후 재검증 |
| 195–225분 | 필요한 발표·설명 자료 | 실제 증거에 연결된 PPT 또는 데모 설명 |
| 225–240분 | 실행 재현과 최종 제출 점검 | 실행 방법, 한계, 본인 설명 |

시간이 줄면 새 기능과 장식을 줄이고 핵심 흐름 검증 시간을 보존한다. 필수 PPT가 없다면 자료 제작 시간을 구현·검증에 돌린다.

## 공개 전 보안 점검과 최종 윤문

| 상황 | 쓸 스킬 | 복사할 요청 |
|---|---|---|
| 외부에 웹·앱 공개 전 | [web-security-check](../../web-security-check/SKILL.md) | `$web-security-check 코드·라이브러리·내 사이트 [URL]·권한 및 배포 설정을 연결해 점검하고 실제 결과와 미실행을 구분해줘.` |
| 발표 대본·보고서 표현 정리 | [humanize](../../humanize/SKILL.md) | `$humanize 이 발표문을 자연스러운 한국어로 다듬되 수치·근거·실패와 미확인 표시는 유지해줘.` |

보안 점검은 공개 전에 시간을 확보해 진행한다. 실제 계정·운영 설정·검사 도구가 없으면 해당 범위는 미확인이다. 윤문은 내용과 근거를 정리한 뒤 적용하며, 표현을 다듬은 결과를 새 검증이나 참가자의 이해 증거로 기록하지 않는다.
