# Probe 고득점 준비 실전 가이드

참가자가 옆에 열어두고 따라가는 가이드다. 핵심은 **문제 파악 → 내 판단 → 작업 위임 → 실제 검증 → 내 말로 설명**이다. 말의 양이나 문서 개수보다 판단의 근거와 실제 결과를 남긴다.

평가항목과 배점은 서로 다른 제출물을 찍은 과거 사진에서 읽은 값이다. 공식 세부 채점 기준을 복원한 것이 아니며 이번 대회의 배점·가중치·수집 범위는 확인되지 않았다. 당일 안내를 우선한다. 아래 행동은 역량을 보여주기 위한 준비 방법이며 점수를 보장하지 않는다. [전사 근거와 해석 범위](rubric.md)

## 시작할 때 복사할 문장

평가받는 Probe 환경의 Codex에 넣는다. 시간과 과제는 실제 안내로 바꾼다.

```text
$probe-hackathon-coach
Probe 실전 모드로 진행해줘. 제한 시간은 4시간이야.
스킬의 references/score-playbook.md를 읽고 고득점 준비 가이드를 적용해줘.
처음에는 전체 시간표와 현재 단계에서 할 일을 간단히 보여줘.

문제와 인터뷰 내용을 확인된 사실·가설·미확인 사항으로 나누고,
핵심 사용자 흐름과 실행 가능한 완료 기준을 정한 뒤 구현하자.
작업은 입력·결과물·완료 기준·의존관계가 드러나게 나눠줘.
중요한 선택에서는 대안과 이유를 설명해 내가 판단할 수 있게 해줘.
새 정보가 나오면 목표·범위·검증 기준을 함께 갱신해줘.

실행한 검증과 아직 실행하지 않은 검증을 구분하고,
기존 기록을 재사용해 중요한 결정과 결과만 간결하게 남겨줘.
중요한 판단과 검증은 이 대화에서도 짧게 설명해줘.
핵심 흐름 완성과 제출 전에는 내가 구조·동작·선택 이유를 이해했는지
한 번에 한 가지씩 질문해줘. 내 답을 네가 대신 작성하지 마.
내가 ‘진행표 보여줘’라고 하면 현재 단계와 다음 행동을 보여줘.

실제 남은 시간:
과제와 공식 안내:
이미 확인한 인터뷰·자료:
```

같은 과제에서는 시작 문장을 반복할 필요가 없다. 스킬을 못 찾으면 설치된 `.agents/skills/probe-hackathon-coach/SKILL.md`를 직접 읽어달라고 한다.

## 지금 어디까지 했는지 확인하기

짧게 다음처럼 요청한다.

| 하고 싶은 일 | Codex에 할 말 |
|---|---|
| 현재 할 일 확인 | `진행표 보여줘. 지금 내가 할 일과 네가 할 일을 나눠줘.` |
| 질문 준비 | `인터뷰 근거를 정리하고 해결 방향을 바꿀 중요한 질문부터 골라줘.` |
| 변경 반영 | `새 사실 때문에 바뀌는 목표·범위·완료 기준을 갱신해줘.` |
| 빠진 근거 확인 | `평가항목 점검해줘. 근거가 부족한 항목과 다음 행동을 연결해줘.` |
| 이해 확인 | `실제 구현의 구조·동작·선택 이유 중 하나를 질문해줘. 내 답 뒤에 피드백해줘.` |
| 전체 가이드 보기 | `고득점 준비 가이드 파일을 열거나 링크로 보여줘.` |

진행표는 현재 기록에서 확인한 내용만 채운다. 아래는 형식 예시이며 완료 증거가 아니다.

```text
현재 단계 / 남은 시간: 확인된 정보 또는 미확인
다음 행동: 최대 3개
내가 판단하거나 설명할 것: 지금 중요한 한 가지
관련 평가항목: 이번 행동과 직접 연결되는 항목
근거 상태: 확인한 결과와 위치 / 부족하거나 미실행인 부분
```

단계 전환이나 요청 시에 보여주고, 모든 답변에 같은 표를 반복하지 않는다. 시간을 모르면 추정해 사실처럼 표시하지 않는다. 단계는 경과 시간만으로 완료 처리하지 않는다.

## 16개 평가항목과 실전 행동

| 평가항목 | 사진 속 배점 | 대화와 결과물에서 보여줄 행동 |
|---|---:|---|
| 기능적 정확성 | 30 | 약속한 핵심 기능을 실제 입력으로 실행하고 결과 확인 |
| 실무적 품질 위험 | 16 | 빈 데이터·잘못된 입력·저장 실패 등 중요한 실패 상황 처리 |
| 제출물 완성도 | 10 | 실행 방법, 사용 예시, 구현 범위, 남은 한계 명시 |
| Output 목표 구체화 | 16 | 누가 무엇을 할 수 있어야 완성인지 관찰 가능한 기준 설정 |
| 재사용 가능한 작업 체계 구축 | 14 | 기록을 이어 쓰고, 입력 규칙·검증 절차·작업 단위를 다른 사례에도 재사용 |
| 의도 갱신 및 맥락 유지 | 18 | 새로운 근거를 얻으면 목표·범위·검증 기준을 함께 수정 |
| 검증 루프 설계 및 통제 | 20 | 예상 결과 설정 → 실행 → 실패 시 수정 → 같은 조건으로 재검증 |
| 문제 상황 및 제약 정의 | 16 | 사용자, 현재 업무, 장애물, 시간·데이터·권한 제약 확인 |
| 작업 분해·위임 설계 | 16 | 작업별 입력, 결과물, 완료 기준과 의존관계 명시 |
| AI 산출물 동작 및 리스크 예측 | 30 | 실행 전에 예상 동작과 실패 가능성을 설명하고 실제 결과와 비교 |
| AI 산출물 구조 이해 | 35 | 입력부터 저장·출력까지 흐름과 핵심 파일 역할을 본인이 설명 |
| AI 의사결정 및 근거 이해 | 35 | 선택한 방식, 대안, 장단점, 선택을 바꿀 조건을 본인이 설명 |
| 정보 활용 | 20 | 인터뷰에서 얻은 사실을 기능과 검증 기준에 반영 |
| 문제 정의 | 25 | 증상과 원인 가설을 구분하고 해결할 문제를 좁히기 |
| 소통 명료성 | 25 | 배경·요청·제약·완료 기준이 드러나는 지시 |
| 요구사항 수집 | 30 | 정상 업무뿐 아니라 예외 상황과 이해관계자 요구 확인 |

배점을 합산해 예상 총점을 만들지 않는다. 자체 점검은 `근거 있음 / 일부 있음 / 없음 / 해당 없음`으로 표시하고 근거 위치와 다음 행동을 붙인다. 파일이 있다는 이유나 AI가 설명했다는 이유만으로 참가자의 역량을 확인 처리하지 않는다.

## 4시간 진행표

아래는 준비용 시간 배분이다. 실제 마감, 이미 끝낸 작업, 필수 제출물에 맞춰 조정한다. 검증과 이해 확인은 구현 중에도 수행한다. 웹·PPT 제작 도구 선택은 [현장 사용 안내](field-guide.md)를 참고한다.

| 경과 시간 | 집중할 일 | 다음 단계로 갈 때 확인할 것 |
|---|---|---|
| 0–30분 | AI 사원 인터뷰 | 최근 사례, 업무 흐름, 제약, 중요한 미확인 질문 |
| 30–50분 | 문제와 완료 기준 확정 | 핵심 흐름, 선택 이유, 제외 범위, 실행 가능한 기준 |
| 50–140분 | 작은 단위로 구현 | 입력부터 결과까지 이어지는 핵심 흐름과 중간 확인 |
| 140–190분 | 실패 예상과 검증 | 예상·실제 결과, 발견한 오류의 수정·재검증 |
| 190–220분 | 본인 설명, 필요한 발표 준비 | 구조·동작·선택 이유의 직접 설명과 실제 근거 |
| 220–240분 | 실행 재현과 제출 점검 | 실행 안내, 제출 형식, 실제 구현·검증 범위와 한계 |

필수 PPT가 있다면 구현 중 확보한 근거를 이용해 준비하고 설명·검증 시간을 함께 조절한다. 시간이 부족하면 새 기능과 장식을 줄인다. 인터뷰가 끝난 상태라면 처음부터 다시 시작하지 않는다.

## ① 인터뷰: 최근 실제 사례부터 묻기

이후 예시는 **‘교대 근무자가 이전 근무자의 미해결 이슈를 파악하기 어렵다’는 가상 과제**다. 실제 SK하이닉스 출제 내용이나 현업 사실이 아니다. 예시 발언을 붙여 넣기 전에 실제 인터뷰와 맞는지 확인한다.

AI 사원에게 물어볼 질문:

- 최근 이 문제 때문에 곤란했던 사례 하나를 처음부터 설명해주세요.
- 그때 어떤 정보를 어디서 찾아야 했나요?
- 시간이 가장 많이 걸리거나 실수했던 단계는 무엇인가요?
- 현재 해결 방식과 그 방식의 불편은 무엇인가요?
- 누가 입력하고, 누가 확인하거나 수정하나요?
- 정상적으로 진행되지 않는 경우에는 어떻게 처리하나요?
- 어떤 상태가 되면 문제가 해결됐다고 판단하실까요?

답을 받은 뒤 Codex에 요청한다.

```text
방금 인터뷰를 근거로 확인된 사실, 우리의 가설, 아직 모르는 것을 구분해줘.
각 사실에는 어느 답변에서 나온 것인지 붙여줘.
해결 방향을 바꿀 가능성이 큰 미확인 질문부터 최대 3개 추천해줘.
```

예를 들어 ‘기록이 여러 곳에 흩어져 있다’는 답만으로 검색 기능이 정답이라고 단정하지 않는다. 추가 답변이 ‘기록은 찾지만 어느 것이 미해결인지 모른다’라면 상태 관리가 더 중요한지 확인한다. 원인과 해결책은 근거가 쌓일 때 갱신한다.

**관련 항목:** 요구사항 수집, 정보 활용, 문제 정의, 문제 상황 및 제약 정의, 소통 명료성.

**단계 확인:** 최근 사례와 제약에 출처가 있고, 중요한 가설을 확인할 질문이 정해졌는가?

## ② 목표: 해결할 문제와 합격 기준 정하기

실제 인터뷰가 뒷받침할 때 참가자가 말할 수 있는 예시:

> 가장 큰 불편은 기록 작성보다 미해결 상태를 파악하는 과정이라고 판단했어. 이번에는 ‘미해결 이슈 확인 → 원문 확인 → 처리 상태 변경’에 집중하자. 자동 알림과 음성 입력은 이번 범위에서 제외하자.

Codex에 요청한다.

```text
이 흐름의 완료 기준을 실행해서 확인할 수 있는 문장으로 작성해줘.
기능마다 인터뷰 근거를 연결하고, 근거가 없는 기능은 제안으로 표시해줘.
가능한 대안의 장단점과 추천 이유를 남은 시간과 데이터 조건에 맞게 설명해줘.
```

| 예시 기능 | 실행 가능한 완료 기준 |
|---|---|
| 미해결 조회 | 예시 데이터에서 미해결 항목만 표시된다 |
| 상세 확인 | 선택한 이슈의 원문과 담당 정보가 일치한다 |
| 상태 변경 | 변경 후 다시 조회해도 상태가 유지된다 |
| 빈 상태 | 미해결 이슈가 없으면 빈 상태 안내가 표시된다 |
| 저장 실패 | 실패한 요청을 성공으로 표시하지 않는다 |

이 표는 검증 계획이다. 실제로 실행하기 전에는 통과로 기록하지 않는다. ‘편하게’, ‘정확하게’ 같은 표현은 확인 가능한 입력과 결과로 바꾼다. 사람이 선택했다는 기록은 실제 발언이 있을 때만 남긴다.

**관련 항목:** Output 목표 구체화, AI 의사결정 및 근거 이해, 정보 활용, 문제 정의.

**단계 확인:** 핵심 흐름, 선택 이유, 제외 범위, 실행 가능한 완료 기준이 있는가?

## ③ 구현: 입력·결과물·완료 기준을 정해 위임하기

```text
다음 순서로 진행해줘.
1. 제공된 사례를 바탕으로 예시 데이터와 필요한 필드를 정리해줘.
2. 그 데이터로 조회·상세·상태 변경이 연결되는 최소 흐름을 구현해줘.
3. 핵심 흐름의 저장 실패와 빈 상태를 처리해줘.
각 작업의 입력·결과물·완료 기준·선행 작업을 짧게 밝히고 진행해줘.
단계가 끝나면 변경 내용, 실제 확인 결과, 남은 문제를 알려줘.
요구사항 변경이나 새로운 외부 서비스가 필요하면 이유와 대안을 먼저 설명해줘.
```

작업 분해는 에이전트 수가 아니라 작업의 경계와 검증 가능성으로 확인한다. 여러 에이전트를 임의로 실행할 필요는 없다. 핵심 흐름을 가능한 한 일찍 처음부터 끝까지 실행한다.

새로운 요구가 실제로 확인됐을 때의 변경 예시:

> 담당자 정보가 꼭 필요하다는 답변이 추가됐어. 기존 목표는 유지하되 목록에 담당자를 표시하자. 추가 작업 시간을 확보하려고 차트는 제외하자. 완료 기준과 작업 계획도 함께 수정해줘.

변경 기록은 `새 근거 → 이전 결정 → 새 결정 → 범위·검증에 미치는 영향`으로 짧게 남긴다. 구현 중 발견한 사실과 사원 답변, 참가자의 선택을 구분한다. 재사용 가능한 입력 규칙이나 검증 절차는 다른 사례에도 적용해본다.

**관련 항목:** 작업 분해·위임 설계, 의도 갱신 및 맥락 유지, 재사용 가능한 작업 체계 구축, 기능적 정확성.

**단계 확인:** 핵심 흐름이 연결됐고 실제로 확인한 결과와 남은 문제가 구분돼 있는가?

## ④ 검증: 예상 동작과 실제 결과 비교하기

참가자가 실제 구현에서 예상한 위험을 바탕으로 요청한다.

```text
상태 변경을 눌렀는데 저장 요청이 실패하면 화면에는 완료로 보일 위험이 있어 보여.
현재 구현이 실제로 어떻게 동작하는지 확인해줘.
문제가 있으면 수정하고 같은 조건에서 다시 검증해줘.
실행하지 못한 검증은 이유와 함께 따로 표시해줘.
```

| 확인 대상 | 예상 결과 | 실제 결과 | 후속 조치 |
|---|---|---|---|
| 정상 상태 변경 | 다시 조회해도 변경 상태 유지 | 실행 전에는 미실행 | 결과에 따라 결정 |
| 저장 실패 | 실패 안내, 잘못된 완료 표시 방지 | 실행 전에는 미실행 | 실패 시 수정·재검증 |
| 데이터 없음 | 빈 상태 안내 | 실행 전에는 미실행 | 결과에 따라 결정 |
| 필수 입력 누락 | 입력 오류 안내 | 실행 전에는 미실행 | 결과에 따라 결정 |

실제 결과에는 실행한 입력·조건과 관찰 결과, 가능한 근거 위치를 연결한다. 실패 상황을 시험하려고 요청 실패를 모의했다면 모의 조건이라고 표시한다. 검증 이야기를 만들기 위해 제품에 결함을 넣지 않는다. 처음부터 통과하면 그 결과를 남긴다.

예시 데이터 검증, 실제 연동 검증, 현업 효과 측정은 다르다. 테스트 통과만으로 업무 시간 단축이나 실사용 안전성을 주장하지 않는다.

**관련 항목:** 검증 루프 설계 및 통제, AI 산출물 동작 및 리스크 예측, 기능적 정확성, 실무적 품질 위험.

**단계 확인:** 예상과 실제 결과가 있고, 발견한 실패는 재검증됐거나 남은 문제로 명시돼 있는가?

## ⑤ 이해: 내 말로 설명하고 실제 구현과 대조하기

핵심 흐름 완성이나 중요한 설계 변경 때도 짧게 확인한다. 아래 요청은 마무리 점검에도 쓸 수 있다.

```text
내가 이 결과물을 이해했는지 확인하고 싶어.
아래 주제로 하나씩 질문하고, 내가 답한 뒤 실제 코드와 다른 부분을 설명해줘.
- 사용자 입력이 어디를 거쳐 저장되고 출력되는가?
- 중요한 판단이나 입력 검증은 어디서 수행되는가?
- 외부 요청이나 저장이 실패하면 어떻게 되는가?
- 선택한 구현 방식의 대안과 장단점은 무엇인가?
- 어떤 조건이 달라지면 지금의 선택을 바꿔야 하는가?
모범답안을 먼저 보여주거나 내 답변을 대신 쓰지 마.
```

답변 후 코드나 실행 결과를 근거로 맞은 점과 수정할 점을 확인한다. 설명을 들은 뒤 다른 입력의 동작을 예측해보는 것도 좋다. 코드가 없으면 개념 연습이며 실제 산출물 이해가 검증된 것은 아니다.

‘직접 설명 확인 / 일부 설명·보완 필요 / 아직 답변 안 함’을 구분한다. 답을 미뤄도 이미 요청한 작업은 진행하고 이해 상태는 미확인으로 둔다. [이해도 점검 방식](explainback.md)

**관련 항목:** AI 산출물 구조 이해, AI 산출물 동작 및 리스크 예측, AI 의사결정 및 근거 이해.

**단계 확인:** 참가자의 실제 설명이 있고, 설명과 구현이 다른 부분을 확인했는가?

## ⑥ 제출: 주장과 증거가 일치하는지 확인하기

```text
최초 목표와 최신 완료 기준을 기준으로 최종 점검해줘.
각 요구사항의 구현 상태와 검증 상태를 별도로 표시해줘.
검증에는 실제 결과와 근거 위치를 연결하고,
README와 발표 내용에 확인하지 않은 주장이 있는지 확인해줘.
실행 방법·예시 입력·실제 연동과 mock·남은 한계를 정리해줘.
공식 제출 안내에 필요한 자료가 실제로 포함됐는지도 확인해줘.
```

최종 표는 아래처럼 구분한다. 실행 결과를 알 수 없는 항목을 완료로 채우지 않는다.

| 요구사항 | 구현 상태 | 검증 상태 | 근거 위치 | 남은 문제 |
|---|---|---|---|---|
| 실제 요구사항 | 완료 / 일부 / 미구현 | 통과 / 실패 / 일부 / 미실행 | 실제 파일·실행 결과·대화 위치 | 확인된 한계 |

발표가 필요하면 **문제와 사용자 → 인터뷰 근거 → 선택·제외 이유 → 실제 시연 → 검증 결과 → 한계** 순서로 구성한다. 측정하지 않은 업무 개선 수치를 넣지 않는다. 예를 들어 예시 데이터에서 조회와 저장을 확인했다면 그 범위만 주장한다.

**관련 항목:** 제출물 완성도, 기능적 정확성, 소통 명료성, 인지 관리 세 항목.

**단계 확인:** 실행 안내가 실제 결과물과 맞고, 구현·검증·설명의 한계가 명시됐는가?

## 최소 기록과 인계

비슷한 문서가 있으면 재사용한다. 필요한 경우 아래 세 파일에만 실제 내용을 기록한다. [기록 형식](records.md)

| 파일 | 담을 내용 |
|---|---|
| `probe-notes/brief.md` | 사용자 문제, 근거, 목표, 제약, 완료 기준 |
| `probe-notes/decisions.md` | 선택한 방향, 비교한 대안, 선택·변경 이유 |
| `probe-notes/evidence.md` | 실행 조건, 실제 결과, 수정·재검증, 미검증 사항 |

핵심 판단과 실제 검증 결과는 평가받는 터미널 대화에서도 짧게 설명한다. 파일 작성이 자동으로 평가 로그 수집을 의미하지 않는다. AI 제안, 사원 답변, 참가자 판단, 도구 관찰 결과를 구별한다.

세션을 넘겨야 한다면 기존 기록을 연결한 인계 문서에 현재 목표·남은 시간·미해결 문제·다음 행동을 적는다. 새 세션에서 그 문서를 읽고 실제 코드 상태를 확인한 뒤 이어간다. 기록을 보기 좋게 정리할 때도 원본 근거 링크를 유지한다.

## 제출 직전 한 번 확인

- [ ] 문제와 핵심 요구사항에 출처가 있다.
- [ ] 내가 선택한 방향과 이유, 제외한 범위를 설명할 수 있다.
- [ ] 최신 완료 기준으로 핵심 흐름을 실제 실행했다.
- [ ] 중요한 실패 상황을 확인했고 미검증 범위를 구분했다.
- [ ] 발견한 오류는 수정 후 재검증했거나 남은 문제로 기록했다.
- [ ] 구조·동작·대안과 선택 이유를 내 말로 설명해봤다.
- [ ] 실행 방법과 제출물이 일치하고 과장된 성과 주장이 없다.
- [ ] 중요한 판단·변경·검증을 평가받는 대화에서도 확인할 수 있다.

체크는 실제 근거가 있을 때만 한다. 공식 항목과 제출 요구가 다르면 그 기준으로 조정한다.
