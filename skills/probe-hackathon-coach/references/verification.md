# 검증 루프

검증은 코드가 존재하는지 확인하는 것이 아니라 요구한 동작이 실제로 일어나는지 확인하는 일이다. 테스트 계획, 실행 결과, 업무 효과를 구분한다.

## 시작할 때

요구사항별 예상 결과를 실행 전에 정한다. 업무 규칙이 미확인인 경우 임의로 정답을 만들지 말고 사원 확인이 필요한 부분과 기술적으로 검증 가능한 부분을 나눈다.

핵심 흐름에는 과제와 관련된 정상·경계·실패 사례를 고른다. 고정된 테스트 개수를 채우기 위한 무의미한 검사는 만들지 않는다.

| 종류 | 선택할 사례 | 확인할 동작 |
|---|---|---|
| 정상 | 대표 실제 입력 또는 명시된 합성 입력 | 합의한 결과와 일치 |
| 데이터 경계 | 누락, 중복, 잘못된 형식, 단위, 시간대·교대 경계 | 조용히 버리거나 잘못 보정하지 않음 |
| 연동 실패 | API 오류, 타임아웃, 권한 부족 | 오류를 설명하고 다시 진행 가능 |
| AI 결과 오류 | 근거 없는 진술, 스키마 위반, 상충 문서 | 검토 필요·근거 부족 표시, 원문 추적 |
| 사용자 흐름 | 새로고침, 재입력, 재시도, 결과 저장 | 상태가 일관되고 중복 조치가 생기지 않음 |

실행 도구가 있으면 실제 실행한다. 코드만 읽었다면 ‘정적 검토’, 실행 못 했다면 ‘미실행’으로 표시한다. mock 응답 테스트를 실제 모델 연동 성공으로 표현하지 않는다.

## 기록 단위

`수용 기준 → 입력·환경·버전 → 예상 결과 → 실제 결과 → 통과/실패/미실행 → 증거 위치 → 수정 → 재검증`

실패하면 재현 가능한 최소 사례부터 만든다. 원인을 추정한 수정은 실제로 실패했던 사례로 다시 확인한다. 마지막 수정 뒤 필요한 재검증을 하지 못하면 그 범위를 남긴다. 관련 없는 전수 테스트 때문에 마감을 놓치지 않되, 핵심 변경의 위험을 검증 없이 통과로 쓰지 않는다.

## 지표

- 누락 탐지: 정답 표본이 있을 때만 precision·recall을 계산하고, 분모·표본 수·미확정 사례를 표시한다.
- 소요 시간: 같은 작업과 조건의 전후 시간을 비교한다. 시연 시간 감소를 현업 전체 생산성 향상으로 확대하지 않는다.
- 문서 답변: 근거의 정확성, 문서 버전, 답이 없는 질문의 처리 여부를 확인한다.
- 인터뷰 피드백: 사전에 정한 기준과 참가자 답변 근거가 연결되는지 확인한다. 언어 유창성과 내용 정확성을 구분한다.

업무 효과를 아직 측정하지 못했으면 기능 검증과 향후 측정 계획만 보고한다.
