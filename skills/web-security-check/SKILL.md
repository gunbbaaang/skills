# Web Security Check

사용자 소유 또는 점검이 허용된 웹·앱의 공개 전 위험을 확인한다. 실제 증거를 바탕으로 먼저 고칠 문제와 아직 확인하지 못한 범위를 짧게 보여준다. 스킬 설치 자체는 검사 실행이 아니다.

## 범위와 준비

- 현재 저장소, 실행 방법, 배포 주소, 사용자 역할, 중요한 데이터, 제공된 테스트 계정을 확인한다. 이미 대화에 있는 정보는 다시 묻지 않는다.
- URL이 없으면 코드·의존성·배포 파일 검토부터 진행한다. 운영 설정에 접근할 수 없으면 저장소의 설정과 운영 중인 설정을 구분한다. 확인할 수 없는 계정·설정은 추정하지 않는다.
- 사용자가 허용한 도메인과 경로에서 필요한 최소 요청만 보낸다. 외부 인증·결제 서비스, 다른 조직의 도메인, 실제 사용자 데이터는 검사 대상으로 넓히지 않는다. 리디렉션도 범위를 확인한다.
- 일반 점검은 읽기 중심이다. 공격형 스캐너, 부하·대량 요청, 운영 데이터 수정은 포함하지 않는다. 권한 확인에는 제공된 테스트 계정과 테스트 데이터만 쓴다. 기존 승인이 해당 검사까지 포함하면 재확인을 요구하지 않는다.
- 사용할 수 있는 검사 도구와 버전을 먼저 확인한다. 없는 도구 때문에 가능한 검토까지 중단하지 않는다. 도구 설치가 필요하면 프로젝트 범위와 기존 권한 안에서 처리하고, 실패한 설치를 검사 성공으로 기록하지 않는다.

## 네 가지 검사를 연결하기

관련 항목부터 수행한다. 기존 검사 결과가 있으면 대상 버전과 환경을 확인해 재사용한다.

| 영역 | 확인할 것 | 필요한 근거 |
|---|---|---|
| 코드 | 서버의 인증·객체 소유권·역할 검사, 입력 검증, SQL/명령 실행, HTML 출력, 업로드, 외부 URL 요청, 비밀키·개인정보 처리 | 파일·함수 위치와 입력부터 민감한 동작까지의 경로 |
| 라이브러리 | 실제 lockfile 기준 직접·간접 의존성의 알려진 취약점, 사용 버전, 수정 버전, 노출 경로 | 실행 명령·도구 버전·종료 코드·보고서·advisory 링크 |
| 실행 중인 사이트 | 공개 경로의 실제 응답, HTTPS·쿠키·헤더·오류 정보, 로그인·비로그인·다른 사용자·낮은 권한에서의 동작 | 환경·URL·역할·기대 결과·실제 결과, 민감값을 가린 증거 |
| 권한·배포 | 배포 환경의 접근 정책, DB·스토리지 규칙, 서비스 계정 권한, 비밀 관리, 공개 파일·관리 화면, 디버그 설정, 요청·비용 제한 | 저장소 설정과 확인한 실제 운영 설정을 별도로 표시 |

`ecc-security-review`가 설치되어 있으면 코드·클라우드 검토의 보충 자료로 읽을 수 있다. `webapp-testing`은 실제 브라우저 확인에 사용할 수 있다. 두 스킬이 없어도 현재 도구로 진행하며, 설치돼 있다는 사실을 검사 증거로 쓰지 않는다.

### 코드에서 볼 핵심

- 화면에서 버튼을 숨기는 것과 서버에서 접근을 거부하는 것을 구분한다. API·DB·스토리지 각각에서 사용자 A가 B의 테스트 자료를 읽거나 바꿀 수 없는지 확인한다.
- 공개 번들·환경변수·로그·오류 응답의 서버 비밀키 노출을 찾는다. 공개용 식별자와 비밀키를 구분한다. 실제 비밀값을 출력·공개 보고서·커밋에 넣지 않는다. 키가 이미 공개됐다면 코드 삭제만으로 해결됐다고 하지 않는다.
- 인증 쿠키를 쓰는 변경 요청의 CSRF 방어, 출력 위치에 맞는 XSS 방어, 업로드 확장자·용량·저장 위치, 사용자 URL 입력의 SSRF 방어를 해당 기능이 있을 때 확인한다.
- AI 기능은 문서·사용자 입력이 도구 실행 권한으로 이어지는지, 검색 결과에서 다른 사용자의 자료가 섞이는지, 요청량·토큰·재시도 비용이 제한되는지 확인한다. 프롬프트 문구만으로 권한 통제가 된다고 보지 않는다.

### 도구와 실제 요청

실행 전 [검사 도구와 결과 해석](references/checks.md)을 읽는다. 현재 프로젝트에 맞는 의존성 검사와 낮은 요청량의 사이트 점검을 선택한다. ZAP Baseline은 선택 가능한 수동 분석 도구이며 로그인 뒤 기능이나 업무 권한을 모두 검사하지 않는다.

로그인·권한 테스트는 아래 경우 중 가능한 것을 직접 확인한다. 단순히 HTTP 200 여부만 보지 말고 응답 본문과 실제 접근 가능 여부를 확인한다.

1. 비로그인 사용자가 보호된 테스트 자료를 요청한다.
2. 테스트 사용자 A가 B 소유의 알려진 테스트 자료를 요청한다.
3. 일반 테스트 사용자가 관리자 전용 읽기 기능을 요청한다.
4. 세션 만료·로그아웃 후 보호된 자료에 다시 접근한다.

계정이나 테스트 데이터가 없으면 해당 검사는 미실행이다. 운영 데이터로 대체하거나 임의 ID를 대량 탐색하지 않는다. 쓰기 권한 검사가 필요한 경우 격리된 테스트 환경에서 기존에 허용된 범위만 실행한다.

## 결과와 후속 작업

기존 검증 기록이 있으면 연결한다. 없으면 사용자가 요청한 위치 또는 프로젝트의 `security-report.md`에 간결하게 남긴다. 원본 스캐너 결과에는 토큰·쿠키·내부 주소가 들어갈 수 있으므로 공개 저장소에 자동 커밋하지 않는다.

보고서에는 대상 커밋·환경·검사 시각, 검사 범위, 다음 표, 우선순위가 높은 조치와 한계를 넣는다.

| 검사 | 상태 | 근거 | 영향·확신도 | 다음 조치 |
|---|---|---|---|---|
| 실제 확인한 항목 | 통과 / 문제 발견 / 실행 오류 / 미실행 / 해당 없음 | 파일 위치 또는 명령·실제 결과 | 재현됨 / 코드로 확인 / 도구 경고 / 추정 | 수정·재검증 또는 필요한 입력 |

- 상태와 심각도를 분리한다. 헤더 하나가 없거나 스캐너가 WARN을 냈다는 이유만으로 침해가 확인됐다고 하지 않는다.
- 먼저 인증 우회·타인 자료 노출·서버 비밀 노출·위험한 입력 실행 등 실제 영향이 큰 문제를 정리한다. 의존성 경고는 앱에서 사용되는 경로와 수정의 영향을 함께 설명한다.
- 수정까지 요청받았다면 필요한 범위만 수정하고 관련 기능·보안 검사를 다시 실행한다. 검토만 요청받았으면 검토 결과를 반환한다. 잠금 파일 대량 갱신, 배포 변경, `audit fix --force`를 임의로 실행하지 않는다.
- 결론은 `발견한 중대 문제 때문에 공개 전 수정 필요`, `확인한 범위에서 중대 문제 미발견`, `핵심 항목 미확인으로 판단 보류`처럼 근거와 연결한다. 취약점 0건을 전체 안전성 보증이나 ASVS 인증으로 표현하지 않는다.
- Probe 모드에서는 중요한 발견·선택 이유·실제 재검증 결과를 평가받는 대화에도 짧게 설명하고 기존 검증 기록에 연결한다. 해커톤 평가 점수를 추정하지 않는다.

## 참고

이 묶음을 위해 작성한 점검 흐름이다. 보안 요구사항의 참고 기준은 [OWASP ASVS](https://asvs.owasp.org/)이며 전체 요구사항 적합성 심사를 뜻하지 않는다. 세부 명령의 출처는 [검사 참고 자료](references/checks.md)에 있다.
