# 검사 도구와 결과 해석

2026-10-31 공식 자료 확인. 실제 설치된 도구의 버전과 도움말을 확인하고 현재 프로젝트의 패키지 관리자·배포 환경에 맞춰 사용한다. 아래 예시는 아직 실행하지 않은 명령이다.

## 라이브러리

- Node/npm 프로젝트는 실제 `package-lock.json`이 있는 프로젝트 루트에서 `npm audit --json`을 실행할 수 있다. npm은 의존성 정보를 설정된 registry로 전송하므로 조직의 외부 전송 제한을 따른다. 네트워크가 없으면 알려진 취약점 검사는 미실행이다.
- 필요하면 `npm audit --omit=dev --json`으로 운영 의존성을 분리하되, 개발·빌드 도구 결과도 배포 과정과 관련 있는지 따로 살핀다. 다른 lockfile을 쓰는 프로젝트에 npm lockfile을 새로 만들지 않는다.
- Python 등 다른 생태계는 실제 requirements/lockfile과 설치 가능한 공식 검사 도구를 확인한다. 예를 들어 `pip-audit`는 현재 버전의 도움말과 지원 형식을 확인한 뒤 쓴다. 도구를 설치하지 못하면 lockfile 수동 검토와 취약점 DB 검사를 구분한다.
- 결과에는 패키지·설치 버전·취약점 ID·참고 URL·수정 가능 버전·앱에서의 사용 경로를 남긴다. 개발용이라는 이유만으로 무시하거나 도구 경고만으로 공격 가능성을 확정하지 않는다.
- 종료 코드가 0이 아니면 보고서를 읽는다. 발견된 취약점 때문에 실패한 것인지, 네트워크·설정 오류로 검사를 못 한 것인지 구분한다. `npm audit fix`는 의존성을 변경하므로 점검 명령으로 사용하지 않는다.

공식 자료: [npm audit](https://docs.npmjs.com/cli/commands/npm-audit/), [pip-audit](https://github.com/pypa/pip-audit).

## 실행 중인 사이트

첫 화면과 관련 API의 실제 응답을 확인한다. `HEAD` 응답이 `GET`과 다를 수 있으므로 화면·API에서 사용하는 요청과 연결한다. 토큰이나 쿠키가 포함된 전체 요청·응답을 채팅이나 공개 파일에 출력하지 않는다.

| 확인 대상 | 해석할 때 주의할 점 |
|---|---|
| HTTPS·리디렉션·혼합 콘텐츠 | 최종 도메인이 허용 범위인지 확인. 로컬 HTTP 개발 환경과 외부 배포를 구분 |
| 쿠키 | 인증·세션 쿠키의 Secure·HttpOnly·SameSite·범위·만료를 용도에 맞춰 검토. 모든 쿠키가 HttpOnly여야 하는 것은 아님 |
| CORS | 허용 origin·자격 증명·응답 내용·실제 브라우저 접근을 함께 확인. 공개 API의 `*`만으로 취약점 확정 금지 |
| CSP·프레임 제한·콘텐츠 유형·캐시 | 앱 동작과 민감 데이터에 비춰 판단. 헤더 존재만으로 XSS나 자료 노출 방지가 증명되지 않음 |
| 오류·소스맵·공개 파일 | 스택·키·내부 경로·개인정보가 노출되는지 확인. 소스맵 공개 자체와 비밀 노출을 구분 |
| 요청·업로드·AI 비용 제한 | 설정과 소량의 허용된 테스트로 확인. 부하 테스트나 실제 고액 API 호출로 한도를 시험하지 않음 |

## 선택 사항: ZAP Baseline

ZAP Baseline은 제한 시간 동안 페이지를 탐색하고 수동 분석한다. 공격형 검사는 하지 않지만 실제 HTTP 요청은 발생한다. 허용된 대상에서만 실행하고, 상태를 바꾸는 GET 경로나 결제·로그아웃·외부 링크가 있으면 범위와 제외 경로를 설정한다. 제한을 보장할 수 없으면 이 스캔은 건너뛰고 허용된 페이지를 직접 확인한다.

Docker 또는 사용 가능한 ZAP 환경이 필요하다. 기존 설치를 우선하고 도구가 없으면 미실행으로 남긴다. Docker의 `localhost`는 컨테이너 자신일 수 있으므로 앱 주소를 실행 환경에 맞춘다.

다음 명령의 자리표시자를 실제 승인된 URL과 미리 만든 절대 경로로 바꾼다. 디렉터리에는 공백이 있어도 되지만 사용 중인 셸에 맞게 인수를 인용해야 한다.

```text
docker run --rm --mount "type=bind,source=<ABSOLUTE_REPORT_DIR>,target=/zap/wrk" ghcr.io/zaproxy/zaproxy:stable zap-baseline.py -t <AUTHORIZED_URL> -m 1 -r zap.html -J zap.json
```

추가 범위 제한이나 인증이 필요하면 공식 문서의 context 설정을 먼저 구성한다. `-n`은 context 파일, `-U`는 그 context에 정의된 테스트 사용자를 지정한다. 인증 없이 첫 화면만 검사한 결과를 로그인 뒤 기능까지 통과한 것으로 표시하지 않는다. 허용 범위를 확인하기 전 Ajax spider나 active/full scan으로 확대하지 않는다.

종료 코드: `0` 성공, `1` FAIL 발견, `2` FAIL 없이 WARN 발견, `3` 실행상 실패. 기본 경고 등급은 WARN이므로 코드 2를 도구 고장으로 처리하지 않는다. 보고서의 경고를 사람이 실제 환경과 대조해 판단한다. 사용 이미지의 실제 digest나 ZAP 버전, 방문한 경로·개수, 검사하지 못한 경로를 기록한다. 움직이는 `stable` 태그는 고정된 버전 번호가 아니다.

공식 자료: [ZAP Baseline Scan](https://www.zaproxy.org/docs/docker/baseline-scan/), [ZAP 시작 안내](https://www.zaproxy.org/getting-started/).

## 권한·배포 설정

앱이 실제 사용하는 서비스만 확인한다. 저장소 설정이 운영에 적용됐는지는 별도로 확인한다.

- DB·스토리지의 공개 읽기/쓰기, 사용자·조직 단위 제한, 서비스 전용 키의 서버 보관을 확인한다. 예를 들어 Supabase의 RLS 정책이나 Firebase의 규칙은 해당 서비스를 쓸 때 검토한다. 설정 파일만으로 실제 계정 간 차단을 증명하지 않는다.
- 배포 계정과 CI의 토큰·권한 범위, 공개 로그, 비밀의 브라우저 전달, 미리보기 환경의 데이터 접근을 살핀다. 토큰 값은 노출하지 않는다.
- 관리자·디버그 경로, 기본 자격 증명, 공개 버킷, 테스트 데이터와 운영 데이터의 분리, 요청·비용 제한을 관련 범위에서 확인한다.
- 플랫폼 콘솔이나 API 읽기 권한이 없으면 운영 설정은 미확인으로 표시하고 필요한 화면·설정 이름을 알려준다. 저장소 검토만으로 실제 클라우드 권한이 안전하다고 단정하지 않는다.

요구사항 참고: [OWASP ASVS](https://asvs.owasp.org/). 특정 요구사항 번호를 보고서에 사용할 때는 확인한 ASVS 버전을 함께 적는다.
